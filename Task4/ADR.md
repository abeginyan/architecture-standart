### **Название задачи:** Передача депозитных ставок в кол-центр банка и в партнёрский кол-центр

### **Автор:** Арам Бегинян

### **Дата:** 02.10.2026

### **Статус:** принято

Этот ADR дополняет `Task3/ADR.md`: он использует те же компоненты (АБС, Kafka, Сервис депозитов, API Gateway) и добавляет только то, что нужно, чтобы операторы обоих кол-центров могли консультировать клиентов по текущим ставкам.

### **Нефункциональные требования**

|**№**|**Требование**|
|:-:|-|
|NFR1|Решение строится на основе текущего процесса работы со ставками: источник ставок остаётся тот же (бэк-офис депозитов, ставка по данным кредитного риска и ставке рефинансирования), меняется только способ доставки. До готовности модуля в АБС источником служит тот же Excel-файл (UC10).|
|NFR2|Кол-центрам передаются только общие (публичные) ставки. Персональные и особые ставки клиентов, а также любые персональные данные в файлы и API кол-центров не попадают.|
|NFR3|Актуальность: ставки в системе кол-центра банка отстают от АБС не более чем на 15 минут. Для партнёра — файл отправляется в течение 30 минут после изменения ставок и обязательно раз в сутки (полный снимок).|
|NFR4|Нагрузка на АБС не растёт: кол-центры читают ставки из Сервиса депозитов, а не из АБС.|
|NFR5|Кол-центр банка продолжает показывать последние известные ставки, если API ставок временно недоступен (копия в базе кол-центра).|
|NFR6|Партнёру доступен только обмен файлами (SFTP). Доставка шифруется (SSH), доступ по ключам, ограничение по IP.|
|NFR7|Файл публикуется атомарно: сначала временное имя, потом переименование; контрольная сумма отправляется последней, партнёр забирает файл только после неё.|
|NFR8|Формат файла версионируется и описан; изменения формата согласуются с партнёром заранее.|
|NFR9|Надёжность выгрузки: повторы с нарастающей паузой, журнал, оповещение при сбое.|
|NFR10|Минимум доработок в системе подрядчика кол-центра банка: достаточно REST-клиента и одного экрана.|
|NFR11|Использовать технологии банка: .NET и MS SQL для Сервиса депозитов, Java и PostgreSQL в системе кол-центра.|
|NFR12|Все выгрузки и обращения к API ставок журналируются (аудит).|

На диаграммах показано только то, что относится к ставкам: остальные части системы из Задания 3 не повторяются. Серым отмечены компоненты, которые уже есть в Задании 3, зелёным — новые, синим — существующие системы, которые дорабатываются.

#### Идея решения

Ставки по-прежнему принадлежат бэк-офису депозитов и в итоге живут в АБС. В Задании 3 они уже попадают в **Сервис депозитов** (в Kafka-топик `deposit.rates`). Мы используем эту копию как единую точку раздачи ставок кол-центрам:

1. **Кол-центр банка** получает ставки по REST API Сервиса депозитов (новый компонент «API ставок»). Система кол-центра раз в 5 минут обновляет у себя копию и показывает её на новом экране «Ставки».
2. **Партнёрский кол-центр** получает ставки файлом по SFTP. Новые компоненты «Планировщик выгрузки», «Формирователь файла» и «SFTP-клиент» создают CSV и отправляют его на SFTP-сервер партнёра ежедневно и при каждом изменении ставок.
3. **Пока модуль ставок в АБС не готов**, ставки попадают в Сервис депозитов через временную страницу ручного импорта Excel/CSV. Так мы сохраняем текущий процесс работы со ставками и не ждём АБС: кол-центры получают ставки уже в начале проекта.

#### Новые и изменяемые компоненты

|Компонент|Что делает|Технология и почему|
|-|-|-|
|**API ставок** (новый, в Сервисе депозитов)|Отдаёт общие ставки и номер версии набора; только чтение; доступ через API Gateway по служебному токену|REST поверх уже существующего каталога ставок. Простой формат, который легко подключить в Java-системе кол-центра|
|**Планировщик выгрузки** (новый)|Запускает выгрузку по расписанию (08:00) и при смене версии ставок|Встроенный планировщик .NET-сервиса|
|**Формирователь файла** (новый)|Читает общие ставки, создаёт CSV (UTF-8, разделитель `;`) и файл SHA-256|CSV поддерживает любая система партнёра; контрольная сумма защищает от повреждённого файла|
|**SFTP-клиент** (новый)|Загружает файл на SFTP партнёра: `.tmp` → переименование → контрольная сумма; повторы при ошибке|Единственный канал, который готов принять партнёр. Банк отправляет файл наружу сам (push), не открывая доступ внутрь периметра|
|**Журнал выгрузок** (новый)|Хранит версию, время, результат, ошибку|Таблица в БД Сервиса депозитов; на её основе строится оповещение|
|**Ручной импорт ставок** (новый, временный)|Загрузка Excel/CSV менеджером бэк-офиса, проверка формата, создание новой версии ставок|Повторяет текущий процесс (Excel), отключается после запуска модуля в АБС|
|**Система кол-центра банка** (дорабатывается)|Периодически опрашивает API ставок, хранит копию в PostgreSQL, показывает экран «Ставки»|Платформа подрядчика допускает расширение; доработку могут выполнить подрядчик и Java-специалисты банка. Пока API недоступен, оператор видит последние известные ставки|
|**Система партнёрского кол-центра** (внешняя)|Загружает файл, показывает ставки операторам|Работа на стороне партнёра; банк передаёт описание формата|

#### Формат файла для партнёра (согласованный формат)

Имя: `deposit\_rates\_YYYYMMDD\_HHMMSS\_v<версия>.csv` и `deposit\_rates\_YYYYMMDD\_HHMMSS\_v<версия>.csv.sha256`.

|Поле|Пример|Комментарий|
|-|-|-|
|`product\_code`|`DEP-12M`|Код депозита|
|`product\_name`|`Выгодный 12 месяцев`|Название|
|`term\_months`|`12`|Срок|
|`currency`|`KZT`|Валюта (согласовано)|
|`min\_amount`|`100000`|Минимальная сумма|
|`rate\_percent`|`14.50`|Годовая ставка|
|`valid\_from`|`2026-10-02T08:00:00`|С какого момента действует|
|`rates\_version`|`128`|Версия набора ставок|

#### Как решение выполняет требования

* **NFR1 (на основе текущего процесса).** Источник и владелец ставок не меняются: бэк-офис депозитов. До АБС-модуля он работает с тем же Excel-файлом, который просто загружается в систему, а не пересылается письмом.
* **NFR2.** Формирователь и API берут только каталог общих ставок: там нет персональных ставок и данных клиентов.
* **NFR3, NFR5.** Кол-центр банка опрашивает API раз в 5 минут и хранит локальную копию. Партнёр получает файл при изменении ставок и ежедневный полный снимок.
* **NFR4.** Ни один из кол-центров не обращается в АБС.
* **NFR6–NFR9.** SFTP по ключам, атомарная публикация файла, версионирование, повторы, журнал и оповещение.
* **NFR10, NFR11.** Подрядчик и банк делают небольшую доработку (REST-клиент и экран); остальное — на технологиях банка.

### **Альтернативы**

|Вариант|Почему не выбран|
|-|-|
|**A. Кол-центр банка читает ставки напрямую из АБС** (БД или API)|Нагрузка на перегруженную АБС и жёсткая связь. Нарушает принцип из Задания 3|
|**B. Кол-центр банка читает Kafka-топик `deposit.rates` напрямую**|Нужно добавлять Kafka-клиент в платформу подрядчика и поддерживать его там; сложнее и дольше. Можно вернуться к варианту после MVP, когда у банка появится опыт с Kafka|
|**C. Продолжать пересылать Excel-файл по почте партнёру (как сейчас внутри банка)**|Вручную, легко потерять или отправить устаревший файл, нет журнала. Но это запасной вариант на случай сбоя SFTP|
|**D. Партнёр сам забирает файлы с SFTP-сервера банка (pull)**|Нужно открывать внешний доступ внутрь периметра банка и поддерживать учётные записи партнёра. Push наружу безопаснее. Согласовано: банк отправляет файл сам (push).|
|**E. Выгрузку делает сама АБС (задание в PL/SQL)**|Дополнительная нагрузка на АБС и привязка формата к АБС. Командой АБС поддерживать такие выгрузки дороже|
|**F. Вынести раздачу ставок в отдельный сервис «Rates Distribution»**|Чище архитектурно, но на MVP это ещё один сервис в эксплуатации. Компоненты можно вынести позже без изменения контрактов|
|**G. Оператор смотрит ставки на публичной странице сайта**|Годится как временный запасной вариант (UC1 из Задания 3), но неудобно: нет единого экрана консультации и ответа на специфические вопросы|

### **Недостатки, ограничения, риски**

|№|Риск или ограничение|Как снижаем|
|-|-|-|
|1|**Партнёр может не загрузить файл или загрузить поздно.** Нет подтверждения приёма: SFTP односторонний|Дата и версия видны в самом файле и в экране оператора; ежедневный полный снимок; в скриптах — «ставки актуальны на дату X»; договорённость о проверке у партнёра|
|2|**Ставки в кол-центре банка и у партнёра могут различаться** на короткое время (у партнёра обновление реже)|Ставки меняются редко (раз в сутки); окно расхождения — до нескольких часов; фиксируем в скриптах и в соглашении с партнёром|
|3|**Сбой SFTP или сети**|Повторы с нарастающей паузой, оповещение, ручная повторная выгрузка, запасной канал (письмо)|
|4|**Изменение формата файла сломает загрузку у партнёра**|Версионирование формата, согласование изменений заранее, тестовая выгрузка|
|5|**Зависимость от подрядчика кол-центра банка**|Минимальная доработка (REST-клиент и один экран); запасной вариант — оператор смотрит страницу со ставками на сайте|
|6|**Задержки с модулем ставок в АБС**|Ручной импорт Excel/CSV позволяет запустить кол-центры без АБС-модуля; отключается позже|
|7|**Ручной импорт: ошибки человека** (неверная ставка)|Проверка формата, предпросмотр, подтверждение, версионирование с возможностью откатить|
|8|**Утечка данных при ошибке в файле** (персональные ставки попали в выгрузку)|Формирователь читает только каталог общих ставок; тесты и проверка перед выпуском|
|9|**Компоненты раздачи ставок живут в Сервисе депозитов**, поэтому его сбой влияет на выгрузку|Сервис работает в двух ЦОД; кол-центр банка хранит копию; партнёр — последний полученный файл|
|10|**Нагрузка на кол-центр** (пожилые клиенты, маркетинговая кампания) не снимается полностью|Отдельное решение: подключение партнёрского кол-центра, скрипты и обучение операторов (задачи T26, T27)|
